01

Le cas est du code typé, avec des unités

Un schéma typé avec autocomplétion et JSON Schema publié. Les unités sont vérifiées, donc une vitesse passée comme Mach est refusée avant toute chose.

Export en TOML, versionnable dans git, comparable avec cfd diff.

crm-hl.pyimport cfd
from cfd.units import m, deg

case = cfd.Case("crm-hl", mesh="crm-hl.cgns")
case.physics = cfd.Compressible(turbulence=cfd.SA(), precision="fp32+acc64")
case.freestream(mach=0.20, aoa=19.57*deg, re=5.49e6, ref_length=7.0*m)
case.boundary("wing.*").wall()
case.boundary("symmetry").symmetry()
case.monitor(cfd.forces("wing.*"), every=10)
02 Inédit en CFD

Planifier avant de calculer

Avant de réserver un GPU, plan vérifie la couverture des conditions aux limites, estime le y+, la mémoire et la durée, et signale les zones à risque.

On ne découvre plus après 40 minutes de file d'attente qu'il manquait une condition aux limites.

terminal$ cfd plan crm-hl.py
  maillage   48,2 M cellules · 71 % polyèdres · non-orth. max 62°
  limites    6/6 surfaces couvertes
  y+ estimé  0,8 (cible < 1) ✓
  mémoire    61 Go/GPU sur 8× B200 · durée ≈ 14 min
  ⚠ W203  première cellule au bord de fuite du volet : y+ ≈ 3
$ cfd run crm-hl.py --gpus 8
03 Inédit en CFD

Des erreurs qui disent quoi faire

Chaque erreur a un code, un emplacement, une correction proposée et une page de documentation.

Une divergence est rattachée à la cellule qui l'a déclenchée, avec sa qualité de maille et la surface voisine. Une commande l'ouvre directement dans le viewer.

04

Des retours en secondes

--preview lance un calcul sur maillage grossier, initialisé par le surrogate, pour voir la tendance avant le vrai calcul.

Suivi en direct partout : interface terminal, widget de notebook, cfd logs -f. Des fonctions Python peuvent intervenir à chaque itération.

critère d'arrêt@case.on_iteration
def stop_when_converged(it, run):
    if run.forces.cl.window(200).spread() < 1e-3:
        run.stop(reason="CL stable sur 200 itérations")
05

Les résultats sont des données

Forces, coupes et champs s'interrogent comme un tableau. La comparaison à l'expérience est une ligne.

Export vers xarray, polars, numpy et torch via DLPack, sans copie, sans quitter le GPU. Les surrogates s'entraînent directement sur les sorties.

post-traitementrun = case.run(gpus=8)
run.forces.cl                                          # série temporelle

cp.compare(cfd.datasets.hlpw5.cp(eta=0.5))         # écart à l'expérience
t = run.surface("wing.*").to_torch(fields=["cp", "cf"])  # zéro copie
06 Inédit en CFD

Différentiable et composable

cfd.grad calcule un gradient exact par adjoint discret sur GPU. cfd.sweep lance des lots de calculs. Les deux se composent comme les transformations de JAX.

optimisationshape = cfd.FFD(case.mesh, box="wing", n=(8, 4, 2))
g = cfd.grad(lambda c: c.run().forces.cd, wrt=shape)   # adjoint GPU

polar = cfd.sweep(case, aoa=[7.05, 11.29, 17.05, 19.57, 21.47]*deg)
polar.plot("cl", against="aoa")
07 Inédit en CFD

Extensible sans danger

Les termes sources et modèles utilisateur s'écrivent en Python. Le même générateur que le solveur les compile en CUDA et en HIP, et produit leur adjoint.

C'est la fonction des UDF en C de Fluent, sans pointeurs ni recompilation manuelle.

kernel utilisateur@cfd.kernel
def actuator_disk(cell, q):
    r = cell.center - disk.center
    return 0.5 * q.rho * cell.volume * thrust_profile(r)

case.source("momentum", actuator_disk)
08

Reproductible par construction

Chaque calcul est identifié par l'empreinte de son maillage, de son cas, de la version du solveur et de sa précision. Un fichier cfd.lock fige tout.

Mode déterministe au bit près, et une commande pour comparer deux calculs.

09

Pensé pour les agents

L'agent utilise exactement la même API que l'humain. Chaque commande sort du JSON, un serveur MCP est fourni, et plan sert de test à blanc.

Documentation disponible en llms.txt. Le JSON Schema du cas permet de valider ce qu'un agent propose avant de l'exécuter.

terminal$ cfd plan crm-hl.py --json | jq .warnings
[{ "code": "W203", "surface": "flap-te", "yplus": 3.1,
   "fix": "case.mesh.prism_layers(first=1.2e-6*m)" }]

Outillage sans friction

  • uv add cfd installe des wheels qui contiennent déjà les binaires CUDA et HIP.
  • cfd doctor vérifie le GPU, le pilote et MPI.
  • Une wheelhouse pour les postes sans réseau.
  • cfd verify lance les solutions manufacturées et la non-régression sur tes cas, avec un plugin pytest.
terminal$ cfd doctor
  GPU      8× B200 · pilote 580.x · CUDA 13
  MPI      GPU-aware ✓
  FP64     faible sur RTX PRO 6000 → précision fp32+acc64 conseillée
$ cfd verify --mms
