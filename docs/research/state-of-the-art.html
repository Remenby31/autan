Interface

Interface visuelle ou DX ?

Les deux, mais dans cet ordre de dépendance. Le gold standard historique est l'interface intégrée de STAR-CCM+ : CAO, maillage, calcul et post-traitement dans une seule fenêtre, avec chaque clic enregistrable en macro. Les nouveaux venus (Flow360, Luminary) ont un SDK Python et une interface web qui pilotent le même modèle de données. C'est cette seconde forme qui gagne.

Tout visuel

  • Indispensable pour l'adoption : personne n'assigne des conditions aux limites à 200 surfaces sans les cliquer en 3D.
  • Seul, il n'est ni reproductible, ni versionnable, ni automatisable.
  • Les agents LLM échouent sur ce qui n'a pas d'API propre : 34 à 68 % de cas corrects sur les fichiers texte d'OpenFOAM.

Tout DX

  • Parfait pour les équipes méthodes, la CI, les plans d'expériences et les agents.
  • Seul, il bloque la majorité des ingénieurs CFD, habitués aux interfaces graphiques.
  • Le maillage, les conditions aux limites et le post-traitement restent visuels par nature.

Recommandation : le cas est du code, l'interface en est une vue

Interface web 3D→Schéma de cas typé←SDK Python · CLI←Agent LLM
  • Une seule source de vérité : un schéma de cas déclaratif et typé, versionnable dans git et validé avant de lancer le calcul (dry-run, erreurs structurées).
  • Chaque action dans l'interface produit le code équivalent, lisible. C'est la macro de STAR-CCM+, en version propre.
  • v1 : SDK, CLI, suivi en direct des résidus et un viewer 3D de résultats. Le post-traitement lourd reste sur ParaView via CGNS et VTK.
  • v2 : éditeur visuel complet (sélection de surfaces, qualité de maillage, conditions aux limites).

Détail par axe

État de l'art

Codes commerciaux

  • Fluent 2026 R1 : GPU solveur pression, 3D, jusqu'à WMLES et SBES. 2,2 Md cellules, 38,5 h → 1,5 h sur 1024 MI250X.
  • STAR-CCM+ 2606 : ségrégé et couplé sur GPU, 1 GPU ≈ 115 à 384 cœurs. Pas d'overset ni d'adjoint GPU.
  • Cadence Charles : LES explicite 100 % GPU sur maillages Voronoi. 1800 WMLES pour HiLiftAeroML.
  • Maillage CPU partout. Licences opaques.

Open source et laboratoires

  • FUN3D : C++ conçu pour le GPU, zéro bibliothèque externe, 73 Md points sur Frontier. ITAR.
  • NASA LAVA : WMLES Voronoi sur GPU, environ 10× moins d'énergie, restée en FP64.
  • SPUMA (OpenFOAM) : port complet CUDA/HIP fin 2025, DrivAer DDES 2,6× moins cher que sur CPU.
  • SU2 : adjoint par AD, CPU uniquement.

Frontière numérique

  • Près de CLmax : dispersion RANS ~0,5 de CL contre ~0,15 en HRLES/WMLES.
  • Plus de dispersion sans données expérimentales : pas de consensus pour la prédiction aveugle.
  • L'adaptation rend les équipes cohérentes, pas plus justes. Aucune n'existe sur GPU.
  • Jalons Vision 2030 probablement manqués : estimation d'erreur, maillage automatique, UQ.

IA et CFD

  • Surrogates DrivAerML : R² Cd ≈ 0,985, ~3,6 counts RMSE. Faibles hors de leur famille de formes.
  • Warm start appris : jusqu'à 16×. AMG appris : +4 à 37 %, rien en production.
  • Agents LLM sur OpenFOAM : 34 à 68 % de cas physiquement corrects.

Matériel

  • NVIDIA réduit le FP64 (B300, Rubin, RTX PRO, GB10). AMD MI430X sera la seule puce FP64 forte, en 2027.
  • Sur ces puces, un kernel FP64 devient limité par le calcul.
  • Bande passante : B200 et MI300X en tête par watt et par dollar.

Marché

  • Consolidation : Synopsys-Ansys, Siemens-Altair, Cadence-Hexagon.
  • Douleurs : préparation du modèle (44 %), coût des licences, robustesse.
  • Startups GPU et IA toutes cloud-first (Flow360, Luminary, PhysicsX).
Limites

Ce qui reste à vérifier

  • Quatre agents ont épuisé leur budget de recherche : specs H100/MI300, prix, MueLu, rocALUTION et PCHPDDM viennent de résumés ou de mémoire.
  • Aucune comparaison publique d'AmgX, hypre et GAMG sur CFD non structurée.
  • Aucune étude atomiques contre coloration sur Hopper et Blackwell.
  • Pas de résumé publié de DPW-8 (juin 2026).
