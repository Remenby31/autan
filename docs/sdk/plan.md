# `autan plan`

`autan plan` checks a case against its mesh before you reserve a GPU. It shows the condition of every boundary and cell zone and where it comes from ([boundary resolution](../contracts/case-schema.md#boundary-resolution)), reports coded [diagnostics](errors.md) and estimates device memory.

```text
autan plan CASE --mesh-info MESHINFO [--gpus N] [--device-kind cpu|cuda|hip] [--json]
```

It exits with 1 when it finds an error. The SDK does not call the mesh readers yet: write the MeshInfo with `autan-mesh-info --json --scale S MESH`, S the case's metres per mesh unit, adding `--ranks N` for a run on N ranks (and `--groups lines` for a steady CPU run with the `lines` solver), and pass it with `--mesh-info` (`E0210` for a MeshInfo written for another run). `plan` compares its `source.sha256` with the hash of the mesh file (`E0203`) and warns when the file is absent (`W0205`). [Check a case before you run it](../guides/check-a-case.md) walks through the output.

## Memory model `autan.memory/2`

The estimate is what one rank allocates at its peak, on the host and on its device, by component; `--gpus` is the number of ranks and `--device-kind` (`cpu`, `cuda`, `hip`, default `cuda`) their device. `bytes_per_gpu` is a rank's host plus device bytes, which share one pool on a unified-memory device such as the GB10, and `bytes_total` that times the ranks. `autan prepare` writes a rank's figures into the solver input (`memory`), and `autan-run` refuses to start a run that does not fit (`E0711`).

Each component counts what the code allocates, listed by the lane that owns it and summed here (#325). Notation, per rank: C cells, F faces, F_i interior faces, F_b boundary faces, K = 2F_i + F_b, S gradient stencil entries (`counts.stencil_entries`; C includes a single rank's `counts.periodic_ghosts`, each with at most `max_faces_per_cell` faces; on several ranks C, F, F_i and S are those of the largest rank of the MeshInfo's `partition`, owned cells and ghosts), n solved equations, s = 4 bytes in `fp32+acc64` and 8 in `fp64`; N nodes, P face nodes (`counts.face_nodes`) and the cell and face counts of the whole mesh where marked *global*.

| Component | Where | Bytes |
|---|---|---|
| `mesh` | host | the global mesh 24N + 16F + 4P + 12F_i + 4F_b + 20C, its FP64 geometry 56F + 32C, colourings 12C, all *global*: every rank keeps them |
| `mesh setup` | host | the reader's form and the MeshInfo pass, about the mesh and its geometry again, which the allocator keeps resident |
| `partition` | host | several ranks: the rank's share of the mesh and geometry, and 9F face keys |
| `mesh reading` | host | while the file is read, beyond the mesh it returns: 3.25 times the mesh's arrays (24N + 16F + 4P + 12F_i + 4F_b + 20C) for Gmsh, Fluent and CGNS, 1.25 times for polyMesh, above « CFD - Noyau maillage »'s measurements (at most 2.99 and 1.19), plus the file's `source.bytes` for the sections a reader skips |
| `renumbered mesh` | host | in RCM order (`quality.lines.order`, the runtime's default) the renumbered copy of the global mesh, as `mesh` without its geometry, and the order and face and point maps 4C + 5F + 4N |
| `solution output` | host | rank 0 gathers 8C *global* bytes per field, and the writer copies them, with the coordinates 24N and the 64-bit connectivity 8 max(F, C) + 8 max(P, K) *global*: the n + 1 primitive fields and their means, the restart's n conserved, n + 1 average sums and their weight, the steady solver's n + 5 values, and one circulation per point-vortex condition |
| `start` | host | a run that starts from a previous one (`autan run --start`) reads its solution on every rank and takes the rank's share: 8(C *global* + C) bytes per field read, every written field for `continue`, the n + 1 primitive fields for `warm` |
| `state files`, `face states` | host | an initial-state file: its text twice at most, 1 KiB of document, 202 bytes per row read and paired, then 160 bytes per cell; a face-state file, measured through the runtime's reader: at most twice its text, 140 bytes per row and 1 200 per zone, then 40 bytes per face of its oracle zones, which a run keeps |
| `physics` | host | packed geometry 8(16F + 4C + 3S), stencil 8C + 4S, state, primitives, limiters, gradients and boundary data in s, solution, stages (a CPU run only), residual in 8 bytes |
| `physics setup` | host | the constructor's packed geometry 8(25F + 4C + 4K) and the stencil's twins and FP64 weights 32S, freed when it returns |
| `device mesh host`, `device setup` | host | on `cuda` and `hip`: the face colourings 4F DeviceMesh keeps; and its setup, with the packed geometry 8(25F + 4C + 4K) it holds until `release_host` after bind, plus the largest of its phases: construction 8K + 8F, the weights' upload 48S + nCs (its FP64 weights and the physics' copy), bind 24S and one staged chunk of 8 MiB |
| `physics device`, `device context` | device, host | on `cuda` and `hip`: the same state, topology, stencil and geometry on the device; 512 MiB for the device context |
| `jacobian` | host | steady runs on `cpu` (a device run solves explicitly): face and cell Jacobians in s, the block matrix 8n²(C + 2F_i) |
| `multigrid`, `lines`, `gauss-seidel` | host | the case's `linear_solver`: the levels below the finest as `quality.multigrid` gives them, 1000 bytes per node and 410 per edge, and the coarsest level's dense LU, 8u² + 8u bytes for its u = 5n unknowns when u ≤ 1000; line smoothing for the MeshInfo's `quality.lines.cells` on the finest level (the multigrid's own count, for the cell order it states) and for every coarse cell when there are lines; the lines built on the whole mesh at setup; the inverse diagonal blocks |

The blocks of the linear solvers are counted for n = 5 and scaled by n²/25. The figures were calibrated on the CPU against measured host peaks (`memory` event of the log, results.md): the multigrid and lines terms on NACA 0012 256², a 48³ hexahedral manufactured solution and the TMR flat plate 137×97 (within ×1.04 to ×1.20 of the measured solver memory), the mesh terms on a 1.17 M-cell tetrahedral mesh. The estimate is for the cell order the MeshInfo states (`quality.lines.order`); a run with another order (`AUTAN_CELL_ORDER`) may form slightly different lines. The model is checked on other cases with two criteria fixed before measuring: **safety**, the estimate at least the measured peak (a refusal must never let through a run that does not fit), and **precision**, at most 1.25 times it. On tet n024, polyhedral n024, NACA 0012 1024² on one and two ranks and the DPW4 CRM grid on a GB10 (Release, spark-5359), declared before measuring, safety holds on every case and precision on none: the estimate is 1.26 to 1.29 times the measured peak on the CPU cases and 1.27 times an upper bound of DPW4's peak on a GB10 (#370). It is conservative, so `autan-run` may refuse a run that would fit; `--allow-oversubscription` starts it, explicitly and logged (`W0712`).
